1. Arquitectura del Monorepo (Turborepo)
La estructura del proyecto es un monorepo gestionado con Turborepo. Esta estructura es estricta y define la separación de responsabilidades. Todo el código que generes debe ubicarse en el lugar correcto.

apps/web: Aplicación Principal (Cliente). Construida con Next.js. Contiene todas las interfaces de usuario, flujos y componentes orientados al cliente final.

apps/api: Backend (Servidor). Construido con NestJS. Gestiona toda la lógica de negocio, acceso a datos y endpoints de la API.

apps/staff: Panel de Administración. Construido con Next.js. Interfaz para la gestión interna, soporte y operaciones.

packages/ui: Librería de Componentes Compartidos. Contiene componentes de React (construidos con shadcn/ui) que se utilizan en apps/web y apps/staff.

packages/db: Capa de Acceso a Datos. Define el esquema de la base de datos (schema.prisma) y exporta el cliente de Prisma para ser usado por apps/api.

packages/config: Configuraciones Transversales. Centraliza configuraciones compartidas como ESLint, TypeScript (tsconfig.json) y definiciones de características (features.ts).

packages/email: Plantillas de Correo Electrónico. Gestiona las plantillas de email construidas con React Email.

3. Estándares de Codificación ("El Sistema Inmune")
El código que no cumpla con estos estándares es considerado inválido.

TypeScript en Modo Estricto (strict: true): El uso de any está terminantemente prohibido. Todo debe tener un tipado explícito y correcto.

Linting y Formato: Todo el código debe ser validado por ESLint y formateado por Prettier antes de considerarse completo. Las reglas de ESLint no deben ser desactivadas (// eslint-disable-line).

Convenciones de Rutas: Utiliza siempre las rutas absolutas configuradas con alias en tsconfig.json.

// ✅ Correcto
import { Button } from '@/components/ui/button';
import { db } from '@repo/db';

// 🚫 Incorrecto
import { Button } from '../../../../packages/ui/src/button';

Estilizado con Tailwind CSS:

Todo el estilizado se realiza exclusivamente con clases de Tailwind CSS.

No se deben crear archivos .css, .scss, o .module.css adicionales.

No se deben usar estilos en línea (style={{...}}), excepto para valores dinámicos que no pueden ser representados por clases de Tailwind (ej. transform calculado en JS).

Diseño de Componentes: Construye todos los componentes de UI utilizando los primitivos de shadcn/ui o, en su defecto, siguiendo su misma filosofía de composición y accesibilidad.

4. Gestión de Estado
La gestión del estado sigue una jerarquía clara para evitar la complejidad.

Estado del Servidor (Server State): Para cualquier dato que provenga de la API, utiliza React Query (TanStack Query). Esto incluye fetching, caching, sincronización y mutaciones.

Estado Global de la UI (Global UI State): Para estado que deba ser compartido entre componentes no relacionados y que no provenga del servidor (ej: estado de un sidebar, tema de la UI, etc.), utiliza Zustand. Debe ser simple y minimalista.

Estado Local del Componente (Local State): Para estado efímero y contenido dentro de un solo componente (ej: estado de un input, visibilidad de un dropdown), utiliza los hooks de React useState o useReducer.

5. Pruebas (Calidad Asegurada)
Las pruebas no son opcionales. Toda nueva funcionalidad, componente con lógica o función de utilidad debe ir acompañada de su correspondiente prueba.

Ubicación: Las pruebas deben coexistir con el código fuente que prueban, utilizando las extensiones .test.ts, .test.tsx, .spec.ts o .spec.tsx.

Framework: Utiliza Jest (o Vitest, según esté configurado en el proyecto) junto con React Testing Library para los componentes.

Ejemplo de Prueba de Componente:

// packages/ui/src/button.test.tsx
import { render, screen } from '@testing-library/react';
import { Button } from './button';
import { expect, test } from '@jest/globals';

test('El botón se renderiza con el texto correcto', () => {
  render(<Button>Enviar Formulario</Button>);
  const buttonElement = screen.getByText(/Enviar Formulario/i);
  expect(buttonElement).toBeInTheDocument();
});

6. Formato de Commits (Conventional Commits)
Todos los mensajes de commit deben seguir la especificación de Conventional Commits.

feat:: Una nueva característica para el usuario.

fix:: Una corrección de un bug.

docs:: Cambios exclusivos en la documentación.

style:: Cambios que no afectan el significado del código (formato, espacios, etc.).

refactor:: Un cambio en el código que no corrige un bug ni añade una característica.

test:: Añadir o corregir pruebas existentes.

chore:: Cambios en el proceso de build, configuración o herramientas auxiliares.

7. Gestión del Historial de Cambios (CHANGELOG.md)
Es un requisito indispensable mantener un registro detallado de todas las modificaciones del proyecto.

Actualización Obligatoria: Antes de ejecutar git commit, o al solicitar la creación de un commit, debes actualizar el archivo CHANGELOG.md ubicado en la raíz del proyecto.

Contenido del Registro: La entrada debe describir de forma clara y concisa los cambios realizados, asociándolos al tipo de commit (ej. feat, fix, refactor).

Formato Histórico: El CHANGELOG.md debe mantener un registro histórico perpetuo. Cada nueva entrada debe añadirse bajo la fecha y hora actual, sin eliminar ni modificar registros anteriores.

Ejemplo de entrada en CHANGELOG.md:

## 2025-07-04 - 17:10

* **feat:** Se implementa el sistema de autenticación con Google OAuth.
* **fix:** Se corrige un error de visualización en el componente de tarjeta de usuario.
* **refactor:** Se optimiza la consulta a la base de datos para obtener la lista de productos.

8. Directrices de Seguridad (No Negociable)
La seguridad es una prioridad máxima.

Cero Secretos en el Código: Nunca incluyas claves de API, tokens, contraseñas o cualquier credencial en el código fuente. Utiliza siempre variables de entorno cargadas desde archivos .env (que están en .gitignore).

Validación de Entradas: En el backend (apps/api), todas las entradas provenientes del cliente deben ser validadas y sanitizadas rigurosamente. Utiliza Zod para definir los esquemas de los DTOs (Data Transfer Objects) y los pipes de validación de NestJS.

Protección de Endpoints: Todos los endpoints sensibles de la API deben estar protegidos por guardias de NestJS (ej. JwtAuthGuard, RolesGuard). Se debe verificar la autenticación (quién es el usuario) y la autorización (qué puede hacer el usuario) en cada solicitud.

9. Flujo de Trabajo y Configuración Local
Gestión de Dependencias: Todas las dependencias se gestionan desde la raíz del monorepo. Utiliza siempre pnpm para instalar, añadir o eliminar paquetes.

Comando de instalación: pnpm install (ejecutado únicamente en la raíz).

Añadir dependencia a un workspace: pnpm add <package> --filter <workspace-name>

Ejecución de Scripts: Los scripts (dev, build, test) se ejecutan desde la raíz usando Turborepo.

Ejemplo: pnpm dev --filter=web

Ejecución Múltiple: Para ejecutar múltiples servicios simultáneamente (ej. api y web), utiliza las capacidades de pnpm o la sintaxis de tu terminal (ej. PowerShell).

Entorno de Base de Datos:

Desarrollo: Durante el desarrollo local, se utilizará una instancia de PostgreSQL instalada directamente en el sistema operativo. No se usará Docker para la base de datos en esta fase.

Producción: El despliegue a producción se realizará mediante Docker y Docker Compose, containerizando todos los servicios, incluida la base de datos.
